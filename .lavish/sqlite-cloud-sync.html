Proposal Phase: review before build

SQLite → Cloud Sync Migration

Add phone ⇄ web sync to the expense tracker. Today it's a local-only expo-sqlite database (9 tables, migration v6) on iOS / Android / Web. The proposal: keep SQLite as the offline-first local engine and sync it to a managed Postgres backend so a single user's data is consistent across all three platforms.

Current
Local-only SQLite
Target
Offline-first cloud sync
Stack
Expo · iOS · Android · Web

Proposed architecture

PowerSync sits between the app and the cloud. The app keeps writing SQL against a local SQLite file (offline-first), PowerSync pushes/pulls changes over a WebSocket to a managed sync service, which writes through to a Supabase Postgres database that also owns auth. Both PowerSync and Supabase have free tiers that fit a single user.

Local layer (unchanged feel)

expo-sqlite keeps running on-device. Queries stay SQL. Reads are instant, writes are local-first, sync happens in the background — the app works fully offline.

Sync layer (new)

PowerSync maps your tables, uploads local mutations, and applies remote changes with conflict resolution. Runs identically on native and web.

Cloud layer (new)

Supabase hosts Postgres with row-level security scoped to the signed-in user, plus the auth flow (email link / password / social).

Biggest change

Integer IDs must become UUIDs

Distributed sync requires client-generated, collision-free IDs. Today two tables use auto-increment INTEGER PRIMARY KEY, which breaks when two devices create a row offline and try to sync. The rest already use text UUIDs (makeId()), which is the correct pattern.

Table PK today Needs change? Why
categories INTEGER Yes → TEXT uuid Created on multiple devices
sources INTEGER Yes → TEXT uuid Created on multiple devices
expenses TEXT No Already makeId()
transfers TEXT No Already makeId()
income_entries TEXT No Already makeId()
budgets TEXT No Already makeId()
exchange_rates currency TEXT Keep local Derived cache — no need to sync
budget_categories (budget_id, category_id) Composite OK Join table, no own identity
budget_history (category_id, month) Composite OK Derived, could stay local
The ripple: converting categories.id and sources.id to UUIDs cascades through every foreign key: expenses.category_id, expenses.source_id, transfers.from/to_source_id, income_entries.source_id, budget_categories.category_id, budget_history.category_id, and categories.parent_id. This is a one-time data migration, not a schema redesign of the feature model.

Migration phases

  • 1 Backend
  • 2 Sync setup
  • 3 ID migration
  • 4 App wiring
  • 5 Cutover
Phase 1

Backend provisioning

  • Create a Supabase project; enable Auth (email-link login, simplest for one user).
  • Create Postgres tables mirroring the app schema, but with uuid PKs on categories and sources.
  • Add a user_id column per table + Row-Level Security so each account only sees its own rows.
Phase 2

Sync engine wiring

  • Provision PowerSync (managed free tier or self-hosted Docker image).
  • Point it at the Supabase Postgres DB; define sync rules listing which tables sync and which stay local (exchange_rates, budget_history).
  • Configure the PowerSync auth connector to accept Supabase JWTs.
Phase 3

One-time local ID migration

  • New migration (v7) in src/db/schema.ts.
  • Generate a stable UUID per existing category/source row (e.g. seeded from slug / name), or backfill via a mapping table.
  • Rewrite all FK columns, then flip the PK column type.
  • Validate: category usage, spending-by-month, budgets, sources, transfers all still report the same numbers.
Phase 4

App wiring

  • Add @powersync/common, @powersync/react-native, and the web adapter.
  • Provide a PowerSyncDatabaseProvider; keep the same query helpers (getExpensesByMonth, etc.) but swap the db parameter type from SQLiteDatabase to the PowerSync wrapper — minimal call-site churn.
  • Wire sign-in on launch; gate the app behind an auth check.
Phase 5

Cutover & verify

  • Ship to one device, confirm initial sync uploads history, then confirm the web app sees it.
  • Test the offline-first loop: enter an expense on the phone with no connection, see it appear on web after reconnect.
  • Remove expo-sqlite dependency once PowerSync owns the local DB.

Risks & open questions

Risks

  • ID migration is the one breaking-data step; needs a careful v7 migration + verification.
  • Conflict resolution defaults to last-write-wins; two devices editing the same category/budget could clobber. Acceptable for a single user.
  • Seed categories (ids 1–8 hardcoded in v1 migration) must map to stable UUIDs or devices could duplicate them.
  • Free-tier limits on PowerSync/Supabase could eventually be hit by a growing history; fine for personal use.
